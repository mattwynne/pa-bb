# Disposable installed BB/Linux note evidence

These scripts are **fixture-only**. They build generated copies of both plugin packages, replace only the generated `server.ts` entry points, install both into fresh BB 0.45.0, and use generated `/tmp` rclone alias sources. Neither entry belongs in a shipped package. Never run against an existing BB data directory or real cloud remote.

On an isolated Linux host with stock rclone v1.75.2, util-linux flock, Node ≥22 and BB 0.45.0, stage a repository snapshot in a disposable directory. Provide `BB_FIXTURE_BB_ROOT` (BB module root), `BB_FIXTURE_SOURCE` (snapshot), `BB_FIXTURE_DEPENDENCIES` (directory containing **read-only** Linux `icloud/node_modules` and `obsidian/node_modules` with SDK 0.6.15), `BB_FIXTURE_PORT` (free loopback server port with its successor also free), and `BB_FIXTURE_ARTIFACTS` (separate generated `/tmp` evidence directory). Run `node fixtures/installed-bb/run-linux.mjs`. The runner preflights **both** ports, excludes ambient auth/provider settings, initializes empty alias baselines with a preparer owner and stops it before the installed entry takes the flock. It adds 24 MiB source bytes only after both plugins are running. The installed entry uses the unchanged production plugin factory with `RcloneProcess(root, '/usr/local/bin/rclone', '512k')`; the wrapper derives `root` from the BB-scoped database's absolute name. This is not a production bandwidth setting.

After `INSTALLED_READY`, connect a private browser tunnel to the fixture's loopback HTTP listener (not a production BB listener). On a Mac with plugin-local Playwright and Chrome, set `BB_REVIEW_BASE`, `BB_REVIEW_CHROME`, `BB_REVIEW_ARTIFACTS` and run `node fixtures/installed-bb/native-review.mjs`. When it prints `PICKER_READY`, create `ui-ready` in the Linux artifact directory; when it prints `NATIVE_UI_COMPLETE`, create `ui-done` there. The UI script performs **no RPC interception**. A failed UI run must not create `ui-done`; the Linux runner fails closed. The Linux runner then explicitly connects the second generated vault, invokes the captured and forwarded nine original tools through its **client-only fixture RPC**, and drives 110+ individually timed saves over five minutes under the real BB minute scheduler. To reproduce a guarded collision separately before the host exits, run `recovery.mjs` on that Linux host with `BB_FIXTURE_BASE` set to its loopback URL and `BB_FIXTURE_ALIAS_ROOT` set to its generated alias root. This auxiliary script writes only the alias, not the mirror.

`result.json` records bounded per-save RPC acknowledgements, actual phase/native-child associations, sampled local application and pending-age observations, native run durations, and exact final logical/alias/mirror SHA-256 comparisons. `summarize-workload.mjs <result.json>` links receipts to sampled applications and native run timestamps without asserting an unobserved individual fsync or cloud delivery. Coalesced saves need not be applied individually; a sampled application is not a following-run retirement. Local fsync and receipt maintenance are **not** separately instrumented. `native-ui.json` and PNG files are generated Mac artifacts. `inspect-settlement.cjs` and `inspect-alias.cjs` are **read-only** post-failure diagnostics accepting an explicit generated scoped database and Linux SQLite dependency; run the latter only after the host/native children stop. Neither diagnostic opens a personal note. Successful cleanup waits for fixture-owned processes; on failure, the runner retains only its generated root for inspection. The driver proves original handler execution through real BB HTTP/SDK caller transport, **not** a model-selected provider conversation, cloud delivery or phone bytes.

For an **independently authorized single generated-data provider conversation, only after the workload and following-run drain pass**, set `BB_FIXTURE_PROVIDER_GATE=1` on a fresh runner. It prints `DRAINED_PROVIDER_READY` and holds the successful installation until a `provider-done` file appears in its artifacts directory. Run exactly one Pi conversation with `--no-builtin-tools --no-extensions -e <private copy of provider-bridge.ts> --no-skills --no-prompt-templates --no-themes --no-context-files --offline --session <private generated session path>`, in a private generated cwd. Make `typebox` and the Pi coding-agent module available to the extension from the **existing Pi installation** (for example with a private read-only `node_modules` symlink); do not install dependencies, copy credentials or modify provider settings. Set `BB_FIXTURE_BASE` to the private loopback tunnel and `BB_FIXTURE_PROVIDER_LEDGER` to a generated private result file. The extension fetches the installed nine original JSON object schemas, registers those names without other tools, and forwards each selected invocation through the actual captured fixture RPC and original Zod parser/handler. Validate model/tool events, complete-read proof and local read-after-save before writing `provider-done`. On failure leave that marker absent: the fixture times out and retains its generated root. The bridge is **not** a normal BB host model-tool-selection API, and is never cloud/device delivery proof.
