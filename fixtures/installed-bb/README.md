# Disposable installed BB/Linux note evidence

These scripts are **fixture-only**. They build generated copies of both plugin packages, replace only the generated `server.ts` entry points, install both into fresh BB 0.45.0, and use generated `/tmp` rclone alias sources. Neither entry belongs in a shipped package. Never run against an existing BB data directory or real cloud remote.

On an isolated Linux host with stock rclone v1.75.2, util-linux flock, Node ≥22 and BB 0.45.0, stage a repository snapshot in a disposable directory. Provide `BB_FIXTURE_BB_ROOT` (BB module root), `BB_FIXTURE_SOURCE` (snapshot), `BB_FIXTURE_DEPENDENCIES` (directory containing **read-only** Linux `icloud/node_modules` and `obsidian/node_modules` with SDK 0.6.15), `BB_FIXTURE_PORT` (free loopback server port with its successor also free), and `BB_FIXTURE_ARTIFACTS` (separate generated `/tmp` evidence directory). Run `node fixtures/installed-bb/run-linux.mjs`. The runner preflights **both** ports, excludes ambient auth/provider settings, initializes empty alias baselines with a preparer owner and stops it before the installed entry takes the flock. It adds 24 MiB source bytes only after both plugins are running. The installed entry uses the unchanged production plugin factory with `RcloneProcess(root, '/usr/local/bin/rclone', '512k')`; the wrapper derives `root` from the BB-scoped database's absolute name. This is not a production bandwidth setting.

After `INSTALLED_READY`, connect a private browser tunnel to the fixture's loopback HTTP listener (not a production BB listener). On a Mac with plugin-local Playwright and Chrome, set `BB_REVIEW_BASE`, `BB_REVIEW_CHROME`, `BB_REVIEW_ARTIFACTS` and run `node fixtures/installed-bb/native-review.mjs`. When it prints `PICKER_READY`, create `ui-ready` in the Linux artifact directory; when it prints `NATIVE_UI_COMPLETE`, create `ui-done` there. The UI script performs **no RPC interception**. A failed UI run must not create `ui-done`; the Linux runner fails closed. The Linux runner then explicitly connects the second generated vault, invokes the captured and forwarded nine original tools through its **client-only fixture RPC**, and drives 110+ individually timed saves over five minutes under the real BB minute scheduler. To reproduce a guarded collision separately before the host exits, run `recovery.mjs` on that Linux host with `BB_FIXTURE_BASE` set to its loopback URL and `BB_FIXTURE_ALIAS_ROOT` set to its generated alias root. This auxiliary script writes only the alias, not the mirror.

`result.json` records bounded per-save RPC acknowledgements, actual phase/native-child associations, sampled local application and pending-age observations, native run durations, and exact final logical/alias/mirror SHA-256 comparisons. `summarize-workload.mjs <result.json>` links receipts to sampled applications and native run timestamps without asserting an unobserved individual fsync or cloud delivery. Coalesced saves need not be applied individually; a sampled application is not a following-run retirement. Local fsync and receipt maintenance are **not** separately instrumented in that five-minute runner. `native-ui.json` and PNG files are generated Mac artifacts. `inspect-settlement.cjs` and `inspect-alias.cjs` are **read-only** post-failure diagnostics accepting an explicit generated scoped database and Linux SQLite dependency; run the latter only after the host/native children stop. Neither diagnostic opens a personal note. Successful cleanup waits for fixture-owned processes; on failure, the runner retains only its generated root for inspection. The driver proves original handler execution through real BB HTTP/SDK caller transport, **not** a model-selected provider conversation, cloud delivery or phone bytes.

For an **independently authorized single generated-data provider conversation, only after the workload and following-run drain pass**, set `BB_FIXTURE_PROVIDER_GATE=1` on a fresh runner. It prints `DRAINED_PROVIDER_READY` and holds the successful installation until a `provider-done` file appears in its artifacts directory. Run exactly one Pi conversation with `--no-builtin-tools --no-extensions -e <private copy of provider-bridge.ts> --no-skills --no-prompt-templates --no-themes --no-context-files --offline --session <private generated session path>`, in a private generated cwd. Make `typebox` and the Pi coding-agent module available to the extension from the **existing Pi installation** (for example with a private read-only `node_modules` symlink); do not install dependencies, copy credentials or modify provider settings. Set `BB_FIXTURE_BASE` to the private loopback tunnel and `BB_FIXTURE_PROVIDER_LEDGER` to a generated private result file. The extension fetches the installed nine original JSON object schemas, registers those names without other tools, and forwards each selected invocation through the actual captured fixture RPC and original Zod parser/handler. Validate model/tool events, complete-read proof and local read-after-save before writing `provider-done`. On failure leave that marker absent: the fixture times out and retains its generated root. The bridge is **not** a normal BB host model-tool-selection API, and is never cloud/device delivery proof.

## Complete ripgrep search correctness

With the same disposable Linux environment variables and stock ripgrep 14.1.0
on the fixture service PATH, run `node fixtures/installed-bb/run-search.mjs`.
It needs no browser handoff, benchmark run or provider conversation. The original
production factories still register/forward all nine tools through the SDK's
verified caller transport.

An independent generator supplies 12,003 notes, more than 16 MiB, hidden and
Git-ignored files, a `.worktrees` folder and a match beyond the former cutoffs.
The fixture checks the exact set of 604 literal matches, 603 typed-property
matches, a two-vault total of 604, query-only folder scopes, a new logical save,
no edit proof from search, and a malformed-YAML query with no reliable total.
It drains every continuation, including pages after complete traversal; count
mode stores no rows. The 0.3.1 fixture includes colon filenames and a colon-named
hidden folder without changing the independent totals. It verifies include/exclude
scopes, complete-read/CAS saves and a pending create there. CAS uses a small
sibling set: the separate existing 10,000-sibling conflict inspection bound is
not lifted by this search fix. Success stops owned children and removes its generated
root. Failed roots are retained. This is an installed original-handler proof,
not BB's model-selector or cloud/device evidence.

## Both-disabled managed update and short timing sample

Run `run-disabled-update.mjs` **separately** in a fresh isolated Linux BB 0.45.0 installation. Archive `plugins/icloud` and `plugins/obsidian` from the deployed old-source commit `2cc7b16` into a temporary directory for `BB_FIXTURE_OLD`; stage the current candidate snapshot, including these fixture entries, as `BB_FIXTURE_SOURCE`. Supply the same `BB_FIXTURE_BB_ROOT`, `BB_FIXTURE_DEPENDENCIES`, free `BB_FIXTURE_PORT` pair and fresh `BB_FIXTURE_ARTIFACTS` as above. Never point either snapshot at a live plugin root. The runner copies the real source into a **temporary local Git repository**, builds fixture-only manifests (`0.1.13-fixture`/`0.1.1-fixture` for the candidate), and installs both by `git:<temporary-repository>@ref:main` with their respective subdirectories. The generated sentinel is a dependency-free ESM plugin: its server artifact metadata is derived from a BB-built fixture package. This is not a production version bump, a path-source reload, a simulated updater, or an `--all` update.

The runner creates two alias baselines with a preparer owner, seeds two genuine v1 note-operation receipts and a previous-version archive through the old installed handlers, connects both named vaults, pauses one selected source, disables both plugins, and waits for disposal. It snapshots byte digests of the stopped iCloud `sync/` store, legacy archive, baselines, opaque configuration/secrets, and the independent sentinel. It advances the temporary Git branch, then imports each candidate bundle in a separate process **without calling its factory**. For each ID it checks the candidate and calls BB 0.45.0's real `/api/v1/plugins/:id/update` managed `applyUpdate` route, awaiting the default stabilization and requiring the raw `applied: true`, `outcome: updated`, and exact Git commit. During each window it polls registrations; before either enable it requires unchanged factory counts, snapshots and absent overlay files/schema. The URL is a private loopback server owned by this fixture, not a remote BB installation.

After both updates finish, the runner enables iCloud then Obsidian, verifies local ownership/readiness and exact legacy receipts, archives and vault IDs, performs an ordinary v2 save/read, and resumes **only** the previously enabled source. It waits for a later successful ordinary scheduled run and checks baseline directory inode/marker identity and the untouched sentinel. Failure stops the fixture host, retains its generated root, and does not downgrade/rebuild or clear any source. Success removes the root after the server and native children exit; the separate private `result.json` and `events.jsonl` remain for bounded verification. The fixture-only timed iCloud entry wraps unchanged overlay `commit`, `maintain`, explicit blob-fsync fault boundaries and directory-fsync method using the same Linux OS monotonic clock (`process.hrtime.bigint`) and AsyncLocalStorage; it records whole commit, explicit Node file/directory fsync, maintenance and client intervals separately. SQLite FULL transaction durability is included in whole commit, **not** measured as a Node fsync. Fresh operations may have no expired receipts to prune: report actual `examined`/`receipts`/`blobs`, never invent aged rows or claim a maintenance deletion that did not occur. No provider conversation is launched by this runner.
