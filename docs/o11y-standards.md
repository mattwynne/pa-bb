# Observability standards

PA for BB should make a failed connection or tool call diagnosable without turning logs into another copy of someone's account. A settings page saying “connected” proves less than a successful provider read; logs must show which boundary failed and help distinguish those states.

- **Name the failing boundary.** Record a stable plugin name, operation or stage (such as OAuth callback, token refresh, catalog discovery, identity lookup, or agent tool call), and outcome. Use BB's plugin logger so timestamps, level, and plugin attribution come from the host. Log a failure where it is handled or suppressed, including background and partial-failure paths; do not double-log one exception at every layer. Do not log routine success or every status poll.
- **Keep diagnostics bounded and safe.** Use fixed categories, known SDK error codes, and validated HTTP or protocol status numbers. Never log a raw exception, stack, cause, provider response, request/response body, OAuth URL or code, token, cookie, client secret, account address, event/file/message content, tool arguments, or unvalidated provider-supplied identifiers. An arbitrary `error.message` or `error.code` is not a safe log field. If a category cannot be determined safely, log `unknown` rather than guessing or exposing data.
- **Separate failure from state.** Distinguish unconfigured or disconnected from transport failure, authorization failure, provider rejection, no usable identity, and a tool that returned an error result. An active connection or cached tool catalog must not be reported as proof that calls work. For multi-account and paginated operations, report partial failure or incompleteness without exposing account IDs or private result data.
- **Keep user feedback useful.** Give the user a safe explanation and recovery step; don't silently turn an operational failure into an empty successful result. Logs can be more specific than the agent/UI response, but neither may contain secrets. Do not claim an uncertain mutation failed or retry it automatically: the provider may have applied it before the error.
- **Prove the boundary.** Test each failure path with synthetic secrets and private provider content in messages, bodies, causes, and structured results. Assert that only the expected bounded category and stage reach the log and that no sentinel leaks. Exercise connection, OAuth, tool calls, and partial results as applicable, including failure after an initially successful connection. Use a harmless live read for deployment verification when available; never require a live write merely to pass this gate.

**Definition of done:** On a fresh or updated BB installation, a failed read or controlled synthetic failure produces an attributable, safe diagnostic at the boundary where it occurred, while the UI/agent receives an honest outcome. Confirm that the plugin log contains neither private content nor credentials, and document what the diagnostic can and cannot establish. If live verification is unavailable, say so; passing unit tests alone is not proof of production observability.
