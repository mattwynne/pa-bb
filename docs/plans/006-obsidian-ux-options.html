Obsidian for BB · Interview draft

What should reading and editing your notes feel like?

Six decisions, concrete examples, and a few alternatives. Use this document to react to the experience before we settle the design.

Proposals, not agreed requirements. All notes, folders, times and outcomes below are synthetic. The mockups are illustrations, not a working plugin or proof of BB support. Only the preference selectors, notes and export controls work.

Keep your reactions: choices and notes are not autosaved. Download interview notes before closing or reloading.

Based on the reading-and-editing plan and its UX review at revision 1eefc6a. The plan has not been revised by this document. BB-style cards and spacing follow existing iCloud settings; the page itself is a standalone discussion aid.

Shared starting point

One vault. Explicit access. No Apple login in chat.

The route to the first useful action

  1. In BB's iCloud settings: connect Apple, choose the vault folder, enable sync and finish its first successful sync.
  2. In Obsidian settings: choose the eligible vault by name. Choose which notes BB can read and edit, then save that authorization.
  3. In chat: ask “Find my notes about the launch.” BB returns permitted sources, not just an answer without evidence.

Initial sync still running? Explain that and refresh while the settings page is open. No eligible mirror is not automatically “no folders selected.”

Safety rules that are not up for trade-off
  • Installing or syncing does not grant Obsidian permission. Whole-vault access is an explicit choice; edits stay within readable scope.
  • An explicit request supplies intent, but a model's assertion of approval is not authorization. No unconditional extra approval step is assumed.
  • Proposals are tied to the whole-note version. Changed notes require a fresh proposal and any required renewed authorization.
  • Uncertain saves are inspected, not blindly retried. Local save, cloud availability and phone receipt are different claims.
  • Creation and edits are included. Renames, deletes, bulk transactions, multiple vaults and community-plugin execution are not.

Decision 01 · Setup and everyday settings

How do you choose what BB may read and edit?

Scenario: let BB read Projects and Meetings, change Projects, and leave Journal alone. The result should be easy to understand before access is saved.

Your tentative preference

Pick readable folders by name. Keep read-only, or separately enable editing for a subset of those folders.

Strength: reading and editing feel like separate grants. Cost: more steps; the same folder may appear in two pickers.

One list of folders, each with No access, Read, or Read and edit. Show the effective permission before saving.

Strength: easier to compare permissions. Cost: nested folders and inherited access need especially clear labels.

Working proposal: start with A and a names-only folder picker. Offer an explicit “Entire vault” choice; suggest read-only, but authorize nothing until Save. Show exclusions and the effective read/edit summary together.

Interview: “Show me how you'd keep Journal private. What would you expect if you selected a parent folder but excluded one of its children?”

Proposed rule: a selected folder includes descendants, exclusions win, and edit access cannot cross an exclusion. Listing folder names for setup needs an explicit permission boundary; it is not permission to index note bodies.

Decision 02 · Making a change

When should BB stop and show you the change?

Scenario: “Mark the ‘Send agenda’ task in Projects/Launch.md complete” is different from “Write up the decision and add it to the project note.” The second request leaves BB to compose text.

Proposed rule for both options

RequestProposed response
Complete one identified task; append exact supplied text to an identified noteSave without a second approval only if BB can verify authorization for that exact change. Then show what changed.
Compose a paragraph, select a destination, or replace a list with assistant-chosen valuesShow the exact destination and change; obtain any authorization still missing.
Ambiguous note or taskAsk which target before preparing or saving.
Note changes while approval is pendingSave nothing from the old proposal. Reread and show a fresh proposal.
Create a meeting note and link it from another noteExplain both edits. Each has its own authorization, save result and receipt; no all-or-nothing promise.

These are proposed examples, not proof that BB exposes trustworthy prior-intent evidence. If that evidence cannot be established, use exact-proposal approval. No option trusts a model-supplied “approved” flag.

For a change that still needs approval, which interaction feels right?

Use the host's enforced approval interaction when needed. Lead with the note and readable change; keep the exact diff available.

Strength: a clear, enforceable save decision. Cost: a separate interaction can interrupt the conversation. Calendar is precedent, not proof this works for every Obsidian session.

Show the draft in chat. A follow-up request to save that exact proposal supplies authorization only if the host can verify and bind it.

Strength: feels like continuing a conversation. Cost: conversational approval is not yet proven enforceable; references like “that” must identify an unchanged proposal.

Working proposal: A where approval is required; no blanket popup for every edit. Explore B in the host spike, not as a promised shortcut.

Interview: “Which of those requests would you expect to save immediately? If BB writes the wording, what would you need to see before it saves?”

Decision 03 · The reply never arrives

How do you find out whether an edit happened?

Scenario: you ask BB to append a decision. The connection drops before its reply. You return in a new chat, with no operation ID. “Try again” could append it twice.

Where would you look first?

Ask about the note or recent edit. BB finds bounded, permitted receipts and asks you to identify the edit if there is more than one.

Strength: no new screen to learn. Cost: you need to know you can ask; exact receipt interpretation must not depend on the model guessing.

Keep the same chat lookup, plus a bounded receipt list in Obsidian settings. This is an operation lookup, not a permanent note-history browser.

Strength: discoverable without remembering an ID or wording. Cost: another UI surface, with retention, empty and unavailable states to design.

The inspection must distinguish these outcomes
  • Saved locally: the durable receipt confirms commit. Later note changes do not erase that historical fact.
  • Confirmed not saved: evidence establishes non-commit. Prepare a fresh proposal against the current note if you still want the change.
  • Still uncertain: evidence cannot establish what happened. Do not replay the edit; arrange inspection of the journal and available file state.
  • Saved, but the note changed afterward: say both. Don't treat matching text or an old hash as proof of the current version.
  • Source unavailable: proposed policy is to allow bounded receipt facts while the same selection and scope remain authorized; refuse content reads and current-version claims. Forgetting or excluding a note revokes receipt access too. This policy still needs a decision and implementation proof.

Working proposal: A first. Every uncertain outcome tells you “Ask me to check the recent edit to this note.” Keep the human-visible note/time and a technical operation ID available, without making the ID the only route.

Interview: “After losing the reply, where would you go? What would convince you it had saved? What should happen if BB still can't tell?”

Decision 04 · A confirmed edit was unwanted

How much recovery should be self-service?

Scenario: BB saved the requested paragraph, but later you decide it was wrong. You have also added a task in Obsidian since that save. Restoring the old whole note must not quietly remove the new task.

What is enough for the first release?

BB identifies the edit and explains recovery. The host operator retrieves the protected copy; restoration requires a comparison and owner authorization.

Strength: smaller release scope and consistent with today's iCloud recovery guidance. Cost: a mistake is not immediately reversible without technical help.

Offer a bounded comparison against the retained pre-edit version. Owner-authorized restoration uses the same scope, version, recovery and coordinated save checks.

Strength: useful recovery without calling an operator. Cost: additional private-copy access and restoration behavior are not in the current tool surface; they need explicit scope and safety design. No automatic merge.

Working proposal: A as the minimum; choose B if operator dependence would make editing unacceptable. Recovery copies are mandatory either way. Retention and capacity limits must be stated before editing is enabled; no duration is promised here.

Interview: “Would you use editing if recovery needed a host operator? Do you mean ‘undo just BB's change’ or ‘restore the complete old version’?”

Decision 05 · Structured metadata

What makes a property change easy to review?

Scenario: “Add ‘Launch plan’ as an alias and replace the tags with project and active.” The alias should be added, not replace the existing alias. Replacing tags removes an existing draft tag.

How much detail should be visible first?

Show named property changes in ordinary terms. Call out additions and removals. Keep the exact YAML diff in a disclosure.

Strength: readable without YAML knowledge. Cost: the summary must remain faithful to the exact source change, including value types.

Keep the same readable summary, with the exact source changes expanded by default for every property preview.

Strength: source fidelity is always visible. Cost: noisier, especially on a phone or for frequent small edits.

Other previews and refusals we need
  • Remove a property: name the key and current value; do not imply removing one list entry.
  • No header exists: “Add a properties header; the body stays unchanged.”
  • Dates and links: preserve the stored date/date-time string; show the link value, with safe YAML quoting. Do not invent timezone conversions.
  • Malformed or duplicate YAML: “The properties header is malformed or ambiguous. No change was saved. Fix it in Obsidian, or ask for an explicit repair preview.” Repairs still need a safely validated result.
  • Unsupported construct: explain that this property cannot be changed without rewriting unrelated formatting; save nothing rather than normalize the whole note.
  • Type expectations: say “stored value,” not “changed the vault's property type.” Private Obsidian type configuration is not available to this plugin.

Working proposal: A. Always make removals visible; leave the exact diff accessible. The choice affects previews when shown, not whether every exact property request needs another approval.

Interview: “What changed in this example? Would you notice that draft was removed? When would you open the YAML diff?”

Decision 06 · After saving

How much sync information belongs in the conversation?

Scenario: the edit is saved locally. A later iCloud sync completes. That alone does not prove these exact bytes reached iCloud, and verified cloud bytes would not prove your phone downloaded them.

Which amount of feedback is useful?

Say what changed and where it was saved. Keep technical IDs and hashes behind inspection. Later status is available when you ask, not a stream of chat notifications.

Strength: light enough for routine edits. Cost: progress is not visible unless you ask or revisit the relevant status surface.

Keep the same receipt, plus a per-edit card whose status can be refreshed from recorded evidence. Do not promise automatic updates until the host supports them.

Strength: evidence is easy to revisit. Cost: more visual weight and host integration; the displayed state must not become a stale success claim.

Exact wording for success, failure and uncertainty
Evidence / conditionProposed wording and next step
Proposed, not committed“Here is the proposed change. Nothing has been saved.”
Declined, cancelled or expired“Nothing was saved.” A new request needs current scope and version checks.
Busy before commit“iCloud is syncing this vault. No edit was saved; try again after it finishes.” Revalidate any later attempt.
Note version conflict“This note changed. No edit was saved; reread it before proposing a new change.”
Local commit confirmed“Saved locally; pending iCloud sync.”
Later sync completed; no content-specific evidence“A later sync completed. Delivery of this version is still unverified.”
This version verified in iCloud, if supported“This version was verified in iCloud. Phone receipt is not verified.” Cloud verification is not promised by this document.
Sync fails after confirmed local save“The edit is saved locally, but sync needs attention. Open iCloud settings. Don't repeat the edit.”
Connection lost around commit“I can't confirm whether the edit was saved. Ask me to check the recent edit to this note before trying again.”

Working proposal: A for the first release. Use truthful destination-specific wording in either design; no “on your phone” claim without device evidence. Automatic notifications and forced sync are not part of this proposal.

Interview: “After ‘saved locally,’ would you expect the note on your phone immediately? Would you prefer to ask about sync, or keep a visible status card?”

Next · A conversation, not a questionnaire

Interview outline and a record of your reactions

Suggested interview flow

  1. Start with real work: which note edits would you ask BB to make most often? Describe them; no private note content is needed.
  2. Walk through setup: choose read/edit scopes and explain what access you think you granted.
  3. Walk through an edit: exact task completion, then assistant-written prose. Identify where you expect a pause.
  4. Break the happy path: lose a reply, encounter a changed note, then recover an unwanted edit.
  5. Check the details: interpret a property replacement and a sync receipt.
  6. Prioritize: what must work before you trust editing, and what can wait?

Ask one question at a time. The choices here are prompts, not a vote: we can combine them or discover a better option. Start with the scenario before showing a working recommendation.

Provisional first-release bundle

Separate reading and editing grants; exact-request consent with host-enforced approval where needed; chat-based save inspection; explicit operator-assisted recovery; readable property comparisons; short local-save receipts.

The two highest-risk assumptions: direct intent can be verified, and operator-assisted recovery is acceptable. Neither is settled.

Before building: settle these journeys and prove the consent/commit boundaries in BB. Measure whether minute-based sync repeatedly interrupts normal edits; do not change scheduling just because it might.

Before releasing: verify real BB desktop/narrow/keyboard states and synthetic save, conflict, uncertain-save and recovery behavior. This standalone document does not pass those gates.
