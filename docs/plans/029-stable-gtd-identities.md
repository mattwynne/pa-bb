# 029 — Stable project and Area identity in Obsidian

**Goal:** Rename a project file or move it from Active to Done in Obsidian, refresh GTD, and find the same conversations under the same project. Moving an Area note within its supported layout must likewise preserve project assignments. Nothing on the read path writes to notes or BB threads.

## One rule for each entity

| | Project | Area |
|---|---|---|
| Landing page, relative to configured folder | `<Status>/<name>.md`, with Status one of Active, Deferred, Someday, Done | `<name>.md` immediately inside the Areas folder |
| Required top-level YAML `id` | `project_<uuid>` | `area_<uuid>` |
| Returned identity | `{source, id}` | `{source, id}` |

The folder says where the note belongs; the ID says which entity it is. A correctly placed note with a missing or invalid ID needs attention; do not invent an ID on read or report a complete inventory that silently omits it. An ID on a supporting note does not make it a project. No README fallback, no folder-only entities. A same-named support folder is optional. Its name is not an identity. Status comes from the project note's parent directory. Use a freshly generated lowercase UUID v4 **once**, on creation or explicit migration, never derived from title, path or status. Retain the existing source/vault boundary; no global cross-vault lookup. A move outside the selected layout is unavailable, not deleted or reassigned.

Example: `Projects/Active/Renew passport.md` has `id: project_c96aa007-7979-405f-bef5-d6b9aab02064`. Moving it to `Projects/Done/Passport renewed.md` changes `notePath` and status, not `id`. For a stable relationship, write `area: area_c83ef831-b035-4c8d-bf8c-aaa26b135690` in the project note; the Area's own `id` has that same value. This is a GTD reference, not an Obsidian wikilink. Human-readable links in note bodies can coexist and do not declare assignments.

**Not in scope:** a copy/duplicate project command, a copy workflow, automatic ID repair, bulk moving support files, or a second vault index. Basic uniqueness validation is necessary for a lookup or edit to identify one note; ambiguity blocks the operation, it does not trigger remediation. Near-instant panel display is a separate performance goal, not a consequence of switching IDs.

## Implementation and rollout

1. **Pin the consumer contract first.** Add fixtures for project and Area lists: stable typed `id`, current `notePath` on every row, display `title`, status for projects and optional stable `areaId`. Preserve source scope and coverage reporting. Version the wire semantics explicitly: today's APIs accept arbitrary strings and some callers interpret IDs as paths. Do not send UUID IDs to an old caller expecting a path. Define which tool/CLI/API versions coexist and how consumers detect unsupported versions before switching defaults.
2. **Build the read path without changing the live default.** Extend the existing GTD Obsidian adapter to request `id` alongside the owner fields it already needs. Build scoped ID-to-note and Area-ID-to-Area lookups from the same authorized inventory. Do not rediscover each ID separately or derive identity from a basename. Resolve project `area` by ID in that inventory. Keep publication/authority checks, partial coverage and live route restrictions from [028](028-obsidian-gtd-indexed-link-plan.md). On incomplete evidence, never guess the target of a write. Obsidian should remain a generic evidence provider; only change it if an integration test identifies a missing primitive.
3. **Convert identity consumers and creation.** Replace path suffix tests and prefix grouping in GTD's [model](../../plugins/gtd/core/model.ts), [adapter](../../plugins/gtd/adapters/obsidian.ts), [Area presentation](../../plugins/gtd/core/area-presentation.ts), sidebar, CLI, agent tools, prompts and skill. Thread metadata keeps `{source,id}`, now with a stable ID. Resolve that ID to the current `notePath` when opening or editing. At write time verify the expected ID on the actual checked note version before the conditional save: path reuse must never redirect an edit. A GTD rename remains a **title edit**, not a physical file move. For explicitly requested new projects/Areas, provide a single creation path/helper that generates the right prefixed ID and includes it in the initial non-overwriting note write. Cover UI/agent creation guidance without requiring a new duplication tool.
4. **Deliver a read-only migration preview first.** Compare the current inventory with the proposed layout. For each legacy root note, grouped note, README-owned entry, empty/attachment-only folder and Area, show the old reference, proposed note location, existing/proposed ID, and exactly which references would change. Reuse valid existing IDs; reserve new ones in a private migration manifest so reruns do not regenerate them. Inventory old `area` declarations and thread associations through supported APIs, including archived threads where accessible. Report coverage gaps. Separate deterministic mappings from choices: missing landing pages, name collisions, nested Area targets with no canonical Area note, ambiguous links, malformed YAML, or files whose identity cannot be proven. Never silently replace a nested target with its enclosing Area. Produce counts and redacted diagnostics; private paths/IDs stay out of source and logs.
5. **Apply only a separately authorized migration.** Keep ordinary service on the old contract until the preview is reviewed. Quiesce competing GTD writes for cutover. Verify source, hashes, destination absence and the reviewed reference mappings again. Use supported version-checked note/property operations, non-overwriting creation, and inspected move plans for any explicitly approved file moves; do not assume note moves carry support directories. Record per-item progress and receipts. Then convert resolved `area` declarations and exact legacy thread references using the manifest, checking current values before each change. Never rediscover an old reference by today's occupant of its old path. Preserve unrelated metadata and historical prompts. Preserve [thread creation receipts](../../plugins/gtd/core/threads.ts): an old request must not spawn a second thread after migration. Reconcile uncertain or interrupted steps by read-back, never blind retry. Test restart/resume on fixtures before any live apply.
6. **Cut over and verify.** Only switch a source to stable-ID mode after comparing inventories and verifying the reviewed mappings and thread counts. Until then clearly identify legacy mode; after cutover, no runtime path/README fallback. A rollback must use a compatible reader and the retained manifest, not simply reload an old build over migrated data. Preserve original files/recovery evidence and document remaining manual exceptions. No live migration is implied by deploying migration-capable code.

## Acceptance and delivery gates

- **Continuity:** on a synthetic vault, link a thread, rename the project file, move it to Done, and put an unrelated note at the old path. After refresh the original thread follows the original ID, the replacement inherits nothing, and a title edit touches only the original project. Repeat Area rename with a linked project. Same source required; moving a note to another vault does not transfer references.
- **Recognition:** only canonical landing pages qualify. Missing/wrong-kind/malformed IDs and ambiguous identity produce actionable bounded warnings and no unsafe edit. Supporting notes are not read as candidate owners. A newly created note has one persistent ID from its first successful save.
- **Migration:** cover every legacy layout, resolved/ambiguous/missing/nested Area relationships, linked and archived threads, stale preview, interruption between note and thread writes, and replay of a prior thread creation request. Verify a second run makes no new identities or duplicate writes. Preview and ordinary inventory produce zero mutations.
- **Compatibility and cost:** test old/new consumers, partially migrated vaults and revoked access. Compare IDs, counts, note paths, assignments, and thread grouping across migration. Measure warm public list latency and RPC count against 028 on the same fixture; stable IDs must not add one filesystem search or RPC per entity.
- **Delivery:** claim affected plugins before source edits, run package tests/typechecks/builds and rendered sidebar checks, follow supported pause/drain and producer-first reload if needed. Verify applied code with harmless reads. The first user-facing handoff is the preview and unresolved decisions, not a changed vault.
