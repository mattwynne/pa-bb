# Google Drive for BB

An independent Google Drive and Docs plugin with explicitly consented full Drive access for a **single-user BB installation**. Connect several Google accounts through an installation-owned Web OAuth client. Calendar and Fastmail remain separate: no credentials, tokens or account records are imported from another plugin or from Pi.

[Connect using your existing Calendar Web OAuth client or a new one](docs/setup.md). Either plugin can copy the other's configured Web client once through a server-only, caller-verified RPC after you register the destination callback. Both save their own copies and account grants, so neither is a runtime dependency. The registered HTTPS callback is `/api/v1/plugins/google-drive/http/callback`; the exact URL is shown in BB Settings. Google's `drive` scope permits reading and modifying accessible files. Existing read-only connections require reconnection and explicit consent before copying or creating; applying code alone does not upgrade their grants. See [copy behavior and authorization](docs/copy.md).

BB's `bb plugin logs google-drive` records bounded stage/status categories for failed identity checks, partial searches, and agent tool failures, without account addresses, OAuth secrets, query terms, or response bodies. A connected identity does not prove that a Drive read will succeed; verify with a harmless read. These diagnostics pass synthetic host tests. A controlled local refusal produces a bounded live log; provider-side failures still need live verification.

[Native document creation](docs/creation.md) supports an explicit account, title, My Drive root or owned unshared folder, and up to 40,000 UTF-16 units of literal multi-paragraph text. It uses existing Drive write consent and the copy tool's user-request authorization, not the Docs-edit approval setting. Keep the single-use operation UUID: interrupted operations may leave a blank or populated Doc, and only read-only status reconciliation is safe. No sharing changes or invitations are made. Provider create/populate writes remain unverified live; delivery uses synthetic disposable fixtures and read-only live checks.

[Local-file upload and modern Office import](docs/upload.md) supports 1 byte–4 MiB regular Linux BB-server thread-storage files only. Exact source/version and shared audience require mandatory owner review; no conversion is inferred. Binary verification uses provider checksums against captured bytes. Explicit XLSX import retains Google's supported formulas/tabs but only checks bounded native evidence, never full Excel fidelity or model correctness. Explicit DOCX/PPTX import creates editable native Docs/Slides through Google, comparing bounded body/slide structure and normalized text, not screenshots. Only modern conservative OOXML is supported; legacy DOC/PPT, OCR and other conversion formats are unsupported. Fonts/layout, tables/objects, animations, media and omitted content remain unverified. Same-name files are not replaced, and uncertain submissions are never replayed.

[Native Sheets](docs/sheets.md) supports bounded new workbooks with literal strings, numeric/boolean/blank cells, civil dates and CAD currency, frozen headers and wrapping. Default destination is root. Existing Drive write consent is reused (`drive` or `drive.file`); the owner must enable Google Sheets API in the existing Google Cloud project. No formula input, scope upgrade, sharing or notifications. Keep the operation UUID and use read-only status after uncertainty; a blank spreadsheet may remain. Only verified confirms title/destination/ordered tabs/cell readback. Real provider writes are not part of delivery testing.

[Existing Sheets editing](docs/sheets-editing.md) changes at most 100 ordinary literal cells in one rectangle after inspection, an exact preview and mandatory owner approval. It preserves existing number formats and notes, rejecting unsupported structures. Validated disjoint merges are allowed; [merged text](docs/sheets-merges.md) supports only one exact top-left plain-string/clear anchor in literal mode, with full bounded footprint/geometry comparison and no unmerge, style or neighboring-value write. Protected/table tabs and merged formulas/typed values remain unsupported. Explicit date/CAD values are supported; [bounded financial formulas](docs/sheets-formulas.md) require `mode:"formulas"` on inspection/edit and `{formula:"=..."}` entries. Ordinary strings including leading `=` stay literal. Formula readback is separate from calculation results/errors; default literal inspection still rejects existing formula cells. The Docs approval setting does not bypass Sheets review. Google Sheets offers no revision/CAS write guard: an external edit racing the last comparison can still be overwritten. One value-only batch is followed by bounded readback. Lost responses retain a durable lock even if current values match; status never retries or unlocks them. Synthetic tests and isolated native-BB approval review do not establish live Google write correctness or that a particular installation has applied these tools.

[Approved sharing](docs/sharing.md) supports named users/groups (reader/commenter/writer) and anyone-with-link (reader/writer, not discoverable), with mandatory owner approval, explicit opt-in invitation emails for named grants, live revalidation and exact readback. Owned My Drive items need complete inspectable ancestry; shared drives and inherited/ambiguous targets are blocked. Folder permissions can affect inheriting contained/future items; no recursive rewrites occur. Unknown writes keep an item-wide durable lock and require read-only status recovery with the same operationId. Google permission mutations have no revision/CAS guarantee here. No real sharing changes or invitations are used for delivery tests; provider writes and recipient access remain unverified live. See [verification evidence and limits](docs/sharing-verification.md).

[Native formatting](docs/formatting.md) supports whole-paragraph font/size/bold/colour, spacing/alignment and tab-explicit opaque page colour, optional Letter size and individual margins. A colour-only `page: {tabId, backgroundColor: "#RRGGBB"}` preserves layout; this is not paragraph shading. Owner approval defaults on and follows the same **Require approval for Google Docs edits** setting as text replacements. The owner can turn it off globally; agents cannot override policy through tool arguments. Scope, revision, durable reservation and verification checks remain on. Page-only changes support bounded structured documents and preserve their complete all-tab representation; paragraph ranges retain strict structural restrictions. It preserves text and unrequested styles with complete all-tab readback, but does not add semantic heading presets, tables, headers/footers or inline wordmark details. Exact font-family readback does not establish actual rendering or menu availability. Keep the operation key: lost-response matching is observation, not proof of completion, and unresolved operations retain a document-wide formatting lock. No OAuth, permissions or approval settings are changed. Synthetic/SSR tests do not establish rendered-BB UX review or live provider-write correctness.

[Native inline images](docs/images.md) add one already-public PNG before an inspected paragraph's existing content, without deleting the wordmark or changing page styles. Explicit tab/revision/index/width, bounded pinned-public-IP HTTPS fetch, existing owner-controlled Docs approval policy and durable read-only recovery apply. PNG only: 8-bit RGB/RGBA, non-interlaced/non-animated, no compressed metadata, ≤2 MiB/4MP. No SVG conversion/hosting, JPEG/GIF, replacement, arbitrary insertion indices, headers or alt-text write. API object/source-URI/size and original-content preservation readback is not proof of embedded bytes or rendering; public URLs can change before Google fetches them. General reading uses image placeholders, strict paragraph editing still rejects images, and page-only formatting remains separate. Build/push does not establish registered availability; delivery uses synthetic tests and isolated no-op UI review, never business document writes.

Search page tokens are **per account**, and `incompleteSearch` and `nextPageToken` must be checked before claiming completeness. Results carry source account and file ID. This slice does not extract text from PDF, Office or Slides. [Bounded filing](docs/filing.md) adds owned My Drive folder creation and existing native/uploaded file moves (Docs, Sheets, Slides, PDFs, images and other movable MIME types), preserving file IDs/URLs. Google move capability is required; shortcuts and folder-tree moves are rejected without following targets or reading file bodies. It inspects inherited access and compares structured audience/role changes to moved files, not shared ancestry alone. Creating an empty folder in an explicitly selected shared destination needs no filing approval for inheritance; this applies to standalone and task folder items and never authorizes later document exposure. The separate filing setting defaults to **Only when access changes**; the owner can choose **Never for filing I request** without weakening capability, verification or recovery checks. Requested batches use one bounded task review with individual durable receipts and honest partial results. Existing destinations only: newly created folders must be verified/inspected before a later move task. It never edits permissions, invites, or changes content. Same-key receipts prevent replay; uncertain moves retain locks. Docs editing, native creation, upload and explicit sharing policies stay separate. Filing delivery/rendered gates must finish before claiming the new source tools are applied. [Docs editing](docs/editing.md) supports only a bounded, uniquely matched replacement within one text run in a selected tab, with exact revision control, owner-controlled per-edit approval and readback. **Require approval for Google Docs edits** defaults on in plugin Configuration; the owner can turn it off globally for all documents/accounts without removing revision or readback checks. General `gdocs_read` output is not edit proof. The editing feature does not change OAuth scopes or upgrade existing grants. Copying requires a separately authorized write grant; destination sharing may be inherited. Google Docs content is untrusted source material, not an instruction to the agent. General reading accepts up to 8 MiB of structured Docs JSON (including formatting), independently of the editing/creation/sharing transport's unchanged 1 MiB limit. Extracted text is returned in pages of at most 100,000 UTF-16 units; follow each `nextCursor` with the same account and document in the same thread until `complete` is true. `truncated` means more projected text remains. Pages are ordered, single-use, and drawn from one short-lived in-memory snapshot; offsets count UTF-16 units and never split surrogate pairs. Expired, replayed or interrupted continuations require a fresh read, which may observe different content. The projection is lossy (including synthetic table separators), does not identify individual tabs, and is never editing proof. Only complete sequential consumption establishes complete delivery of this projection, not all document content or currentness. Responses beyond the transport limit fail with a distinct size-limit message and `response_too_large` diagnostic, not a connection warning; download the Doc as plain text as a read-only workaround. Provider error bodies, OAuth codes and tokens must not reach logs, UI or tool errors.

```sh
npm install

npm run typecheck
```

The core uses injectable storage, OAuth and provider ports; the BB adapter stores separate Drive account/pending tables. Docs and Sheets creation share a durable native-file lifecycle and adapter-private creation/scope policies, preserving existing Docs receipts. Creation, editing and permission mutations share adapter-private HTTP, scope inspection, timeouts and bounded response decoding in `adapters/docs-transport.mjs`. Each adapter retains its own allowed write scopes and rejection rules; core services still receive only narrow document/sharing operations, never an arbitrary HTTP proxy. The [Gherkin acceptance feature](features/oauth-client-reuse.feature) runs both plugin servers under fake BB hosts to check client reuse in either order; the cross-plugin test builds Calendar's sibling package in this monorepo. Host tests use synthetic tokens and Google responses. Real Google sign-in and provider-session reads remain to be verified after an installation owner configures the Web OAuth client. Do not use this plugin on a multi-user BB installation until BB can enforce per-user isolation.
