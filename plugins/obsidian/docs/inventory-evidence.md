# Inventory evidence v1

This consumer-driven plugin contract serves GTD, not agent content reads. GTD owns project ownership, the lowercase `area` declaration grammar, Area membership and IDs. Obsidian owns path syntax and source authority. Production consumers keep independent wire schemas; no implementation imports cross the plugin boundary.

`status.inventoryEvidenceVersion === 1` negotiates three distinct single-operation RPCs, restricted to the GTD plugin caller:

- `inventoryChildren`: `vaultId, root, folder` → immediate `entries` (`name, kind`), `incomplete`.
- `inventoryProperties`: `vaultId, root, path, fields` → `status` (`observed`, `missing`, `partial`), `properties`, `unsupported` field names. An observed absent property differs from a missing owner. A per-field bound does not discard other usable properties. Up to eight scalar list elements, each string up to 4096 characters, preserves eight valid 1024-character declarations without the recursive projection's aggregate 4096-character bound.
- `inventoryTarget`: `vaultId, root, path, reference` → `status` (`matched`, `missing`, `ambiguous`, `unsupported`, `incomplete`), bounded `matches` (`path, kind`), normalized `basename` or null, `fragment`, `embed`, `incomplete`. Bare note names compete throughout the root; explicit paths can report both a note and directory. GTD applies note precedence and its immediate bare-folder rule. Optional metadata is not required.

Every reply includes `authority` (`revision, route, epoch`) and `publication` (UUID on the indexed route, null on live routes). Requests can carry `expectedAuthority` and `publication`. These restrict continuing authority; they grant nothing. Each operation holds one lease, rechecks the connected source and lease before return, and closes it on every exit. No read or edit proofs are issued.

GTD sends continuity fields after its first operation, then reacquires children after assembly. A changed indexed publication is rejected, not silently mixed or automatically retried. The UUID is process-local publication identity, **not** an epoch or cloud generation. Live routes retain independent local observations, not atomic snapshot semantics. Ready sources with grant v1 use the index; older supported direct and logical routes use authorized live operations. Refusal, revocation or mid-inventory rollback never selects a weaker fallback. Known partial owners/children retain independent confirmed results; failed authority discards the entire assembled inventory.

Older consumers retain unchanged strict `listChildren`, `listProperties`, `projectAreas` and `projectAreasFromFrontmatter` responses. `listChildren` now derives names from the authorized view where eligible, including empty directories. Missing folders and potentially hidden immediate children are partial. Malformed properties do not hide a known child's name. Updated GTD uses the verified frontmatter-only relationship route only if new capabilities are absent at initial negotiation. The single-operation RPCs also remain available for existing consumers.

## Indexed batch evidence

`status.inventoryBatchVersion === 1` advertises batching alongside the existing capabilities. GTD can obtain the same inventory capability flags and connected vaults from `inventoryStatus(null)`, which reads the catalog without traversing receipts. Both inventory RPCs are restricted to the GTD plugin identity.

`inventoryBatch` accepts `vaultId`, `root`, optional `expectedAuthority` and `publication`, and an ordered array of 0–128 requests. Each request uses the fields of the corresponding single-operation RPC plus a `kind` of `children`, `properties`, or `target`. The response carries one authority and publication stamp and a row per request in order, with the matching `kind` and single-operation evidence fields. An empty request array verifies access and returns an empty row array. A successful live probe returns its non-index authority with a null publication. GTD can use that route information with its existing root check and single-read flow.

Each indexed batch checks its selected nested root against the leased publication. The root must contain a directory named `.obsidian`. An ancestor marker, including one at the mirror root, takes precedence. The depth limit is 32 components, and paths through `.obsidian`, `.git` or `node_modules` are excluded. Omissions affecting the selected ancestry or checked markers make the proof inconclusive and cause refusal. Unrelated omissions still affect evidence under the single-read rules. The empty root needs no marker. This checks a specific indexed path, so it has no unrelated full-discovery traversal cutoff. Marker observations can lag disk changes until the index publishes. Every indexed read and empty probe uses the same check and independently revalidates the authorized source and lease.

An indexed batch takes a fresh catalog observation for admission and reuses it for configuration confirmation. Before returning, it drains a second fresh catalog observation and the final lease check in parallel. The final grant verifies the current iCloud admission revision, mirror membership and pinned root. The batch then checks route, epoch, revision, cancellation and lease validity. A warm producer fixture uses seven iCloud RPCs per indexed batch, down from twelve. Live routes and the single-read RPCs keep their existing authorization sequence.

The response cap is 4 MiB of UTF-8 JSON, including the evidence stamp. Existing row-level bounds and partial flags still apply. Above the aggregate cap Obsidian rechecks access and refuses the entire batch. BB returns code `invalid` with an issue at `["requests"]` carrying the fixed token `output_limit`. Split those requests and keep the same authority and publication. Other failures discard the attempted evidence. A nonempty live batch is refused with code `invalid` and issue token `incompatible` at the same path. Obtain a successful empty live probe before choosing the single-read flow.

## Verification and cost

The cross-package synthetic contract tests in `test/filesystem-vault.test.ts` drive GTD's public list RPCs through the actual producer schemas and services. They cover warm nested-root operation without local data I/O, ownership, large declarations, old/new parity with 51 owners, direct/indexed authority, intersecting omissions, rollback and safe diagnostics. Pure projection tests cover clipping and field bounds. Existing Area, legacy routing, lease, grant and agent-follow tests remain regression gates.

A synthetic 51-owner run (52 indexed notes) used 55 data RPCs for sparse declarations and 105 for dense declarations, versus four on the old batched route. Setup/status were measured separately. Observed elapsed times in one local run: indexed old/new sparse 128/75 ms, dense 79/135 ms; direct sparse 166/177 ms, dense 154/358 ms. These are fixture measurements, not production latency promises. The single-owner/single-reference API deliberately pays more RPC overhead for dense declarations; supporting-note reads are eliminated. Matching still scans the immutable catalog, with no publication lookup map. Do not infer a batching requirement from one run. A later live check reached the existing 20-second deadline with sequential owner RPCs. GTD now prefetches owner properties and resolves independent owners with at most four concurrent jobs per phase, draining entered work on failure before discarding results; the single-operation wire contract is unchanged. A subsequent live read completed within the deadline. Prefetch promises are inventory-local buffers, not a persistent cache. Target-catalog instrumentation on the 52-note fixture records 52 entries examined for one explicit reference and 2652 for 51 references; this excludes owner lookup and child projection scans.

The focused producer tests compare mixed batch rows to the single RPCs, exercise nested-marker precedence, check indexed and live authorization, and verify structured capacity refusal with UTF-8 accounting. The 51-reference batch examines each of the 52 indexed notes once. It stores only requested lookup keys, up to two bare-name candidates per key, and paths of immediate children for requested folders. Those lookups live for the batch only. A warm empty probe scans no notes.
