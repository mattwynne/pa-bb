# Fastmail for BB

One-install, single-account BB 0.45+ plugin. It connects directly to Fastmail's official `https://api.fastmail.com/mcp` with `@modelcontextprotocol/client` 2.0.0 (MIT); it does **not** load Agent Plugins or depend on the experimental fixture. BB's `@get-bb/plugin-sdk` is a host API/dev dependency, not an embedded bridge. The existing Google Calendar plugin remains independent.

Install **Fastmail** from PA for BB, then follow the [setup guide](docs/setup.md) from its settings page. Choose the grant at Fastmail. A browser on another machine will fail to open the `localhost` redirect; copy the **entire address from that browser's address bar** into the password-style paste-back field in BB. Never paste that address into chat, logs, or a support ticket. The plugin checks the exact loopback origin/path, one-use state and expiration before delegating PKCE/issuer verification and exchange to the MCP SDK. Start again if the callback fails. The normal localhost callback route is also one-use and returns only a generic success/failure page.

The connection screen shows its state, tool count, and the address Fastmail's `list_identities` tool explicitly marks as the **default sending address**, when available. Other identities may be aliases; even the default sender is not proof of the login username. If no single default is available, the screen says so. If you use multiple Fastmail accounts, verify which one you authorized in Fastmail's sign-in tab. The login grant controls available tools. A read-only grant exposes only the provider's read tools; a broader grant can expose writes and sends. This plugin does not impose tool-name filters or another Fastmail-specific confirmation gate. It advertises the provider's *runtime* JSON schemas as BB agent tools after connection (for new sessions). `fastmail_list_tools` and `fastmail_call_tool` provide a fallback for schemas BB cannot register, and discover/call current grant tools by provider name. There is no static copy of the Fastmail catalog. BB agent tool/session rules still apply. Provider content is untrusted; check provenance and account/calendar context. A failed mutation may already have succeeded: inspect before retrying. Agent-visible tool errors and OAuth failures remain generic. BB's plugin logs record only the failing stage and a fixed error category (or bounded HTTP/JSON-RPC status), never raw provider messages, tool arguments, account addresses, callback URLs, or tokens. `identity_lookup no_default_sender` means the identity call completed but no usable default address was found; it does not establish which account was authorized. Check `bb plugin logs fastmail` on the BB host when diagnosing a failure. Before a tool call on a connection older than 25 minutes, the plugin opens a fresh MCP connection if no other call is active. This is a precaution based on an observed failure roughly 53 minutes after connection, not proof of a Fastmail session lifetime. If a call still receives HTTP 500, the plugin reconnects for subsequent calls but never retries the failed call. A read may need a deliberate retry; a mutation may have completed remotely, so inspect Fastmail before retrying it. The `connection_reset` log records only a bounded connection-age bucket, session presence, negotiated protocol version, and a validated Fastmail trace ID if the response supplies one (otherwise `trace=none`). These fields help investigate recurrence but do not prove why Fastmail returned 500. The upstream cause remains unconfirmed.

**Disconnect** closes the connection and deletes local OAuth credentials; revoke the remote grant separately in Fastmail's security settings. BB Disable/Remove unloads the plugin, closes its connection, and removes its tools. Disable preserves BB's plugin data so re-enable can reconnect; Remove deletes the BB plugin data. Reload/restart preserves credentials in BB's plugin-owned local SQLite DB, which is not separately encrypted (as with Google Calendar); protect BB's data directory and backups. BB's secret settings suit static user-entered secrets, but this SDK synchronously reads/writes changing tokens, client registration and discovery state. The settings API is asynchronous (`get`/`experimental_set`), so moving individual fields there without an atomic cache/write protocol risks stale or lost refreshes and callback races. No such migration is attempted here. The auth callback has no BB session by design and is protected by one-use state/PKCE. This plugin should only be installed by the single user who owns that BB installation.

The MCP SDK's tool transport and provider scopes determine permissions. The plugin does not advertise client sampling/elicitation/roots capabilities: if a provider tool requires an unsupported interaction, the SDK fails the operation rather than silently agreeing or inventing an approval. This limitation is **not** evidence that every future Fastmail mutation flow is supported. Do not claim writes have been live-tested. Schema/catalog changes apply on a new BB session; a stale tool name is checked against the current live catalog at execution. The generic catalog is a fallback for BB's 256-tool/128-KiB-schema limits. Discovery walks at most 32 pages, 2048 tools and 4 MiB of tool definitions; an incomplete or oversized catalog revokes the prior selection instead of presenting a partial grant.

Local verification: `npm ci && npm test && npm run typecheck && npm run build`. Tests use synthetic OAuth/MCP servers and fake credentials, never a Fastmail account. An isolated BB 0.45.0 local-path install, disable/enable, RPC status and remove were checked without connecting an account; marketplace manifest validation found two independent entries. Managed Git install from the marketplace can be tested only once the Git ref includes this package. No production PA BB changes or grant changes were made.
