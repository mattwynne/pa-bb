# Migrate project status to folders

Establish the baseline with the previous GTD reader still loaded. Get separate authorization for live vault changes. Use the configured Projects scope and exact source and note IDs throughout. Keep the migration record private. Coordinate a quiet period for moves and note edits. If automatic dated reactivation is enabled, coordinate its temporary suspension and review dates before restoring it. A legacy root project moved into Deferred can become eligible for reactivation.

## Record the current classification

1. List all statuses with `gtd_list_projects` or `bb gtd projects --status all --json`. Follow every cursor with the same filter. Require complete coverage and a unique ID for each project. Confirm that the configured Projects scope identifies project landing notes. If Projects overlaps Areas or includes notes with an ambiguous role, resolve which notes are in scope before writing. Record each exact ID, returned status and resolved Area, along with any new path and operation IDs as work progresses.
2. If coverage is partial, stop. Resolve the reported source, scan limit, duplicate ID or frontmatter problem before using the list as a baseline. In the previous reader, an unsupported root status value can exclude a note and make coverage partial. Inspect the immediate Projects notes if necessary. Have the owner resolve the intended classification of any previously unclassified note before starting cleanup. Repeat the full inventory after resolving blockers.
3. For projects already in a recognized status folder, keep the path. For instance, `Projects/Active/Example.md` with `status: completed` stays Active. Root notes reported as Active also stay at their current paths. Root notes reported as Deferred, Someday or Done must move first. For example, `Projects/Example.md` with `status: completed` is Done under the previous reader and must go into Done or Completed.

If complete coverage already confirms that every root project is Active, the baseline also serves as the classification check for upgrading. Removal of redundant properties can follow separately when authorized.

## Move first, then remove the property

1. For each root project that needs to move, complete an `obsidian_read_note` of its exact landing note. Follow all continuations, including any final acknowledgement, and require `complete` and `editReady`. Check the root note’s top-level status against the recorded classification. The previous reader recognizes the exact values `deferred`, `someday`, `done` and `completed` for these moves.
2. Pass the complete-read hash as `expectedHash` to `gtd_prepare_project_change`, along with the exact `source`, `id` and recorded status. Check the returned destination and record the plan ID before calling `gtd_apply_project_change` once. Use this GTD move for both standalone and paired projects. GTD checks destination ownership, moves the landing note and its same-stem companion folder, preserves the resolved Area and updates the captured BB thread references. The move leaves thread archive state alone.
3. A missing or ambiguous status folder, including simultaneous Done and Completed destinations, an occupied destination note or companion path, or incomplete thread evidence blocks the move. Resolve the specific blocker under the migration authorization, then take a fresh inventory and note version before preparing another plan. For a conflict or interrupted move, inspect `gtd_check_project_change` using the original plan ID and check the original Obsidian receipts. Use `finishLinks: true` to resume eligible remaining steps. Wait for `links_verified` and confirm the new ID, its status and its Area in GTD. Resolve any pending move or reference repair before editing the destination note. If the move was definitively refused, recheck the source, version and destination before preparing again.
4. At each confirmed current path, complete a fresh `obsidian_read_note`. For a top-level `status` entry on its own line in supported block-style YAML, call `obsidian_update_properties` with the exact `vaultId`, `path`, `expectedHash` and `remove: ["status"]`. Use only confirmed project landing notes. Treat inline maps, unusual key layouts, unsupported YAML and notes that exceed write limits as blockers for review. For a supported document with an inline map, a reviewed, unique exact replacement via `obsidian_edit_note` can remove just that entry using the same complete-read version. Keep the save operation ID. Compare the complete before and after texts to verify that unrelated YAML, comments and Markdown were preserved.
5. If the write conflicts or the reply is lost, check `obsidian_status` and resolve any pending receipt through `obsidian_recover_receipts`. For a lost operation ID, inspect outstanding receipts and match the exact vault and path before proceeding. Require a definitive outcome and a fresh complete read before another write. If the field is already absent on a verified note and no operation is pending, skip the edit.

## Verify before upgrading

After any moves, take a new complete GTD inventory under the previous reader. Compare it with the baseline using the recorded old-to-new path mapping. Account for every project and confirm its status and resolved Area. Check that every attempted status move and property save is settled. Every project still directly under Projects must be Active. Recheck coverage and the mapping if source notes changed during the migration. If verification is incomplete, keep the previous reader loaded.

Once the comparison passes, deploy the folder-only reader and run a fresh read-only inventory. Compare statuses and Area assignments again and check the status filters. To finish property cleanup, verify that every current landing note has had its top-level property checked and reconcile any outstanding saves. The operation receipts verify local outcomes. Confirm cloud or device delivery separately if it is part of the rollout.
