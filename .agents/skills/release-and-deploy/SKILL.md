# Release and deploy

The default end to implementation in this repository is **verify → commit → push → release → deploy → observe**, not “code complete, awaiting a separate request.” Do this without asking for routine permission, but honor any explicit review, release or deployment hold. Follow `../../../AGENTS.md` and `../../../docs/o11y-standards.md`; for any plugin UI change also load `../bb-plugin-ux/SKILL.md`. Its rendered-BB review remains a release gate even if tests pass.

1. Review the diff and working-tree status. Stage only your own changes; never include someone else's concurrent edits. Run the affected package tests and typechecks, plus applicable shared checks. Preserve user data and grants. Stop and report any failing gate rather than shipping unverified code.
2. Commit on `main` and push to `origin/main`. **A push is not a release.** For plugin changes, publish the intended component release under [ADR 0002](../../../docs/adrs/0002-component-releases.md) before deployment; do not release unrelated work present in the repository. If the shared pipeline or released source is unavailable, report that blocker rather than deploying unreleased `main` or enlarging credential permissions. A Git marketplace refresh does not release or update installed plugins. Use the deployment identity and access method in the operator's private infrastructure notes. Keep hostnames, addresses, machine IDs, usernames and provisioning paths out of public documentation. Check `bb plugin outdated` and verify that the native candidate is eligible released code before `bb plugin update <id> --yes`, **never `--all`**. If that native command would install unreleased code, stop rather than substituting a version label for release proof. Documentation-only changes need neither a component release nor a plugin update. BB snapshots plugin state before an update, but that is not a substitute for checking the result.
   **Quiesce background sync before update preparation.** For a plugin that can write files, remember which folders were enabled, use its supported Pause controls to prevent new scheduled runs, and let any active run finish. A point-in-time idle status check does not reserve an update window: another run can start during candidate preparation. If supported controls cannot quiesce it, stop and report the blocker. When the installed iCloud/Obsidian pair lacks updater-aware Pause, use its documented stopped paired upgrade; never bypass the capability check. After updating, restore only the previously enabled folders through normal Resume controls and observe a completed run. Never clear failed state, locks, or baselines merely to deploy; recovery needs separate inspection and explicit consent.
3. Confirm that the actual installed version/source belongs to the published component release, that the plugin is running, and that existing credentials and other plugins remain intact. Exercise a narrowly scoped **read-only** RPC or tool call; inspect plugin logs for bounded errors without printing private results or secrets. Do not perform a live mutation merely to prove a deploy. For UI changes, inspect the rendered BB page in relevant states and widths with keyboard navigation; if that cannot be done, say the UX gate is unverified rather than claiming release complete.
4. Report the shipped commit, component release tags, installed versions, tests, live observations, and any unverified gate or rollback. If the server is unreachable or deployment fails, say what did and did not ship. Seek user input only for an actual blocker, risky migration, or consequential action outside the requested work.

Do not log OAuth callbacks, tokens, account addresses, provider bodies, or arbitrary exception messages while diagnosing production. Do not auto-retry uncertain writes.
